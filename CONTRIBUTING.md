
# Contributing to CODEX

Thank you for your interest in contributing to **CODEX — Quantitative Adversarial AI Security Evaluation Framework**.

Contributions are welcome from developers, researchers, security enthusiasts, and documentation contributors.

This document explains the contribution process and the standards expected for proposed changes.

---

## 1. Project Goals

CODEX aims to provide a structured and evidence-based framework for:

- Adversarial prompt analysis
- Jailbreak technique classification
- Prompt injection research
- Quantitative security evaluation
- Model resistance assessment
- Evaluation reporting
- Defensive AI security research

All contributions should support these objectives.

---

## 2. Ways to Contribute

You can contribute in several ways.

### Bug Reports

Report issues involving:

- Incorrect analysis results
- Scoring inconsistencies
- Documentation errors
- Unexpected behavior
- Classification problems
- Reproducibility issues

Include clear steps to reproduce the problem whenever possible.

### Feature Suggestions

Suggestions may include:

- New analysis categories
- Improved evaluation criteria
- Additional scoring methods
- Better reporting formats
- Documentation improvements
- Usability enhancements

Explain the problem your suggestion addresses and how the proposed feature would improve CODEX.

### Code Contributions

Code contributions should prioritize:

- Readability
- Maintainability
- Reliability
- Reproducibility
- Clear documentation
- Appropriate testing

### Documentation Contributions

Documentation improvements are welcome.

Examples include:

- Clarifying evaluation methodology
- Improving scoring explanations
- Adding examples
- Correcting technical inaccuracies
- Documenting limitations

---

## 3. Contribution Standards

All contributions should follow these principles.

### Accuracy

Do not introduce unsupported technical claims or fabricated evaluation results.

### Transparency

Clearly distinguish implemented functionality from proposed functionality.

### Consistency

Follow existing naming conventions, formatting, and project structure.

### Reproducibility

Provide enough information for others to understand and verify proposed changes.

### Security

Treat submitted adversarial prompts as untrusted data.

Do not introduce functionality that secretly executes specimen instructions or misrepresents evaluation results.

---

## 4. Pull Request Guidelines

Before submitting a pull request:

1. Review the existing project documentation.
2. Understand the functionality being modified.
3. Make focused changes.
4. Test relevant functionality.
5. Update documentation when necessary.
6. Explain the purpose of the changes.
7. Include relevant testing information.

Pull requests should describe:

- What changed
- Why it changed
- Which files were affected
- How the changes were tested
- Any known limitations

Avoid combining unrelated changes into one pull request.

---

## 5. Code Quality

Contributed code should:

- Use descriptive names.
- Avoid unnecessary complexity.
- Include appropriate error handling.
- Avoid undocumented behavior.
- Follow the existing project architecture.
- Include tests where practical.

Do not claim that a feature is functional unless it has been implemented and appropriately verified.

---

## 6. Evaluation Integrity

CODEX prioritizes evidence-based security analysis.

Contributors must preserve the distinction between:

- Static analysis
- Behavioral testing
- Demonstrated effectiveness
- Model resistance
- Evaluation confidence

Missing behavioral evidence must not be replaced with fabricated scores.

Evaluation reports should clearly communicate uncertainty and limitations.

---

## 7. Documentation Requirements

Changes affecting project behavior should include corresponding documentation updates.

Relevant documentation may include:

- README.md
- limitations.md
- methodology.md
- scoring.md
- classifications.md

Documentation should accurately describe the current implementation.

---

## 8. Communication

When reporting problems or proposing changes:

- Be respectful and constructive.
- Provide relevant technical details.
- Avoid unsupported accusations.
- Explain disagreements with evidence.
- Focus on improving the project.
